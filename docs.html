Introduction

TYPE/262 switches on the DNS WALLET record so any domain can be resolved, verified and paid on Robinhood Chain.

TYPE/262 makes every domain a wallet. You publish one DNS record that names your address. Any person or AI agent can then resolve your domain to that wallet, check that a payment address really belongs to you, and pay your name in USDG or ETH on Robinhood Chain.

The record is already part of DNS. WALLET is resource record type 262, allocated by IANA on 2024-06-21, but almost no software reads it yet. TYPE/262 makes it usable today: an SDK and CLI that resolve it, a _wallet TXT fallback that any DNS dashboard can publish, and contracts that let a domain receive money before its owner has published anything.

What you can do

  • Make your domain payable. Publish one record, turn on DNSSEC, and your domain resolves to your address. Start with the Quickstart.
  • Pay a name instead of an address. Resolve a domain, confirm that the resolvers agree and the answer is DNSSEC-signed, then send USDG or ETH. See Payments.
  • Check an x402 payTo. Before an agent pays an HTTP 402 requirement, verifyPayTo confirms that the address is published by the domain it is talking to. See Agents and x402.
  • Pay a domain that has not published yet. The money waits in DomainEscrow until the owner claims it with a DNSSEC proof that the contract checks on-chain. If nobody claims it, the sender can take it back 180 days after their last deposit. See Escrow.
  • Launch a token that pays a domain. Launch on pons v2 with creator fees routed to a domain instead of a wallet. See Launchpad.

Trust model

  • Resolving and paying trust the DNSSEC validation of the DNS-over-HTTPS resolvers (Cloudflare and Google), cross-checked against each other. See Resolution.
  • Escrow claims trust no resolver. The contract verifies the DNSSEC chain on-chain, anchored to the IANA root keys, and pays only the wallet the proof shows. See DNSSEC proofs.
  • The escrow admin can pause new deposits and hand the admin role to another address. It cannot move funds, change who gets paid, or block claims and refunds, which keep working while deposits are paused.

Get started

Quickstart

Make your domain payable from the app in a few minutes, then resolve and pay any domain from code.

There are two ways in. If you own a domain, make it payable from the app. If you are building, resolve and pay any domain from code with the SDK.

Make your domain payable

You need a domain whose DNS you control and an EVM wallet address. Use a regular wallet address, not a multisig or smart-contract wallet: other software reads the ETH code and may pay that address on Ethereum or another EVM chain.

  1. Open Publish. Go to app.html#publish and enter your domain. A URL or an email address also works; the app reduces it to the host name. Keep the default TTL of 1 hour, or pick 5 minutes or 1 day.
  2. Pick a network and paste your address. Leave the network on Robinhood Chain and paste your 0x address, or click Use my wallet to fill it from a connected browser wallet. Paste a Bitcoin or Solana address and the network switches for you; Other takes any coin code of 2 to 16 characters. Click + Add another address to publish more than one.
  3. Add the TXT record at your DNS host. Copy the record the app shows: type TXT, name _wallet, content ETH 0x…, and your TTL. For a subdomain such as shop.yoursite.com, the name is _wallet.shop. Some hosts want the full name, _wallet.yoursite.com.
  4. Turn on DNSSEC. Enable DNSSEC at your DNS host. On Cloudflare: DNS, Settings, Enable DNSSEC. If your registrar is a different company, add the DS record Cloudflare shows you at the registrar.
  5. Check that it is live. Click Check it's live, which opens app.html#resolve/yoursite.com. You should see your address tagged _wallet TXT and Signed, a DNSSEC ✓ tag, and 2/2 resolvers agree.

The record you add is equivalent to this zone-file line:

_wallet.yoursite.com. 3600 IN TXT "ETH 0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"

Under Other formats, the app also shows the native WALLET record and its RFC 3597 generic form for DNS software that supports them. The WALLET record explains all three.

Publish the TXT form even if your DNS host supports type 262. The app's escrow claim proves the _wallet TXT record, so a domain with a signed TXT record can claim escrow payments and launch fees right away. See Escrow.

You can run the same check from a clone of the repository:

node bin/type262.mjs resolve yoursite.com
yoursite.com  DNSSEC ✓  resolvers agree
  ETH    0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de  (TXT, signed)
If Resolve shows Unsigned zone, DNSSEC is not active yet: your address still resolves, but payers see a warning and escrow claims stay disabled. If it shows No wallet here. Yet., your DNS host has not published the record yet, or the name is wrong.

Resolve and pay from code

The SDK is one zero-dependency ES module, wallet262.js, for browsers and Node 18 or later.

1. Get the SDK

curl -O https://type262.onrender.com/lib/wallet262.js

Save it next to your code. It imports nothing, so there is nothing else to install.

2. Resolve a domain

// resolve.mjs, saved next to wallet262.js. Run: node resolve.mjs
import { resolveWallets } from './wallet262.js'

const r = await resolveWallets('yoursite.com')
console.log(r.verified, r.records)
// true [ { code: 'ETH', address: '0x7a1f…c0de', source: 'TXT', dnssec: true } ]

verified is true only when the domain publishes at least one record, every resolver that answered returned the same records, and every record is DNSSEC-authenticated. Resolution covers every field of the result.

3. Pay it

In a browser with an injected wallet, find the domain's EVM address, switch the wallet to Robinhood Chain, and send USDG. transferTx builds the EIP-1193 transaction parameters for a native or ERC-20 transfer.

import { resolveWallets, addressKind, transferTx } from './wallet262.js'

const USDG = '0x5fc5360d0400a0fd4f2af552add042d716f1d168' // 6 decimals
const ROBINHOOD = {
  chainId: '0x1237', // 4663
  chainName: 'Robinhood Chain',
  rpcUrls: ['https://rpc.mainnet.chain.robinhood.com'],
  blockExplorerUrls: ['https://robinhoodchain.blockscout.com'],
  nativeCurrency: { name: 'ETH', symbol: 'ETH', decimals: 18 },
}

async function payDomain(domain, amount) {
  const r = await resolveWallets(domain)
  if (!r.agree) throw new Error('Resolvers disagree about this domain. Not sending.')
  const rec = r.records.find(x => addressKind(x.address) === 'evm')
  if (!rec) throw new Error(`${r.domain} publishes no EVM wallet`)
  if (!r.verified) console.warn(`${r.domain} is not DNSSEC-verified. Double-check large amounts.`)

  const provider = window.ethereum
  const [from] = await provider.request({ method: 'eth_requestAccounts' })
  try {
    await provider.request({ method: 'wallet_switchEthereumChain', params: [{ chainId: ROBINHOOD.chainId }] })
  } catch (e) {
    if (e.code !== 4902) throw e // 4902: the wallet does not know this chain yet
    await provider.request({ method: 'wallet_addEthereumChain', params: [ROBINHOOD] })
  }
  if (parseInt(await provider.request({ method: 'eth_chainId' }), 16) !== 4663) {
    throw new Error('Switch your wallet to Robinhood Chain first.')
  }

  const tx = transferTx({ from, to: rec.address, amount, decimals: 6, token: USDG })
  return provider.request({ method: 'eth_sendTransaction', params: [tx] }) // the transaction hash
}

const hash = await payDomain('yoursite.com', '5')

Load the script as a module (<script type="module">) from a page served over HTTP. ES modules do not load from file:// URLs. For ETH instead of USDG, omit token and use decimals: 18.

The app's Pay tool applies the same rules: it disables sending when resolvers disagree and warns when the zone is not DNSSEC-signed. From a terminal, the CLI prints an EIP-681 payment link that a wallet can open, and warns on stderr when the record is not DNSSEC-verified by every resolver:

node bin/type262.mjs link yoursite.com 5 USDG
ethereum:0x5fc5360d0400a0fd4f2af552add042d716f1d168@4663/transfer?address=0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de&uint256=5000000

Records

The WALLET record

How the WALLET record is encoded, the three ways to publish it, and which coin codes count for payments and escrow claims.

A WALLET record maps a domain name to one payment address for one coin. TYPE/262 reads it in two places: the native type 262 record at the domain itself, and a TXT fallback at _wallet.<domain> for DNS hosts that cannot create type 262 records yet. Both carry the same two values, a coin code and an address.

Wire format

WALLET RDATA is exactly two <character-string>s, the coin code and then the address, with the same wire format as TXT. Each string is one length byte followed by up to 255 bytes of data.

FieldEncodingExample
Coin codeLength byte, then ASCII03 45 54 48 (ETH)
AddressLength byte, then ASCII2A 30 78 37 61 … (0x7a…, 42 bytes)

The SDK rejects anything else. parseWalletRdata throws A WALLET record must hold exactly two strings for one or three strings, Empty coin code or address when either string is empty, and Malformed generic RDATA, RDATA length mismatch or Truncated character-string for broken generic RDATA. encodeWalletRdata throws Each string must be at most 255 bytes. Coin codes are uppercased on both encode and parse.

Named form

DNS software that knows type 262 by name accepts the record as two quoted strings:

example.com. 3600 IN WALLET "ETH" "0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"

Generic form (RFC 3597)

Servers that do not know the WALLET mnemonic accept the record in the generic form from RFC 3597: the type is written TYPE262 and the RDATA \# <length> <hex>. This works today on BIND, Knot, NSD and PowerDNS.

encodeWalletRdata produces the RDATA, and zoneLines produces complete zone-file lines in all three forms:

import { encodeWalletRdata, zoneLines } from './wallet262.js'

const address = '0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de'

const { bytes, generic } = encodeWalletRdata('ETH', address)
console.log(bytes.length) // 47
console.log(generic)      // \# 47 034554482A307837613166653163326230643361346635653664376338623961306631653264336334623563306465

const lines = zoneLines('example.com', [{ code: 'ETH', address }]) // TTL defaults to 3600
console.log([...lines.generic, ...lines.named, ...lines.txt].join('\n'))

TXT fallback at _wallet

Most DNS dashboards cannot add a type 262 record yet. Publish the same coin code and address as a TXT record at _wallet.<domain> instead:

_wallet.example.com. 3600 IN TXT "ETH 0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"

The SDK (parseFallbackTxt) and the on-chain verifier (DnssecVerifier.walletAddress) both accept three layouts:

LayoutExample
One string, separated by a space"ETH 0x7a1f…c0de"
One string, separated by a colon"ETH:0x7a1f…c0de"
Two strings"ETH" "0x7a1f…c0de"

In the one-string layouts, the coin code comes first, then one or more spaces or colons, then the address. Nothing may follow the address. For these layouts the SDK accepts codes of 2 to 16 characters drawn from letters, digits, ., _ and -. A TXT record the SDK cannot read in any layout throws Unrecognized _wallet TXT format and ends up in invalid.

The TXT record must sit at _wallet.<domain>. A TXT record at the domain itself is ignored by both the SDK and the verifier. Keep the _wallet name for wallet entries only, because the SDK reads every TXT record there as a coin code and address pair.

The verifier also accepts a DNSSEC-signed native WALLET record at the domain itself. The app's claim flow builds its proof for the _wallet TXT record, so publish the TXT form if you want to claim from the app. See DNSSEC proofs.

Coin codes

A coin code names the chain or asset an address belongs to. Codes are case-insensitive, and the SDK uppercases them. Any code is valid in DNS, but only EVM codes take part in Robinhood Chain payments and escrow claims.

Ten codes count as EVM. The list is identical in EVM_CODES in lib/wallet262.js and in DnssecVerifier.isEvmCoin: ETH, EVM, HOOD, USDG, ARB, OP, POL, USDC, USDT and DAI.

For an escrow claim, the verifier also requires the address to be exactly 0x followed by 40 hex digits. Anything else in the signed record set, such as a BTC or SOL line, a note, or a longer hex string, is ignored and can never be claimed to.

The Publish tab uses it to reject mismatches. resolveWallets returns records as published, without this check.

Publish a regular wallet address under ETH, not a multisig or smart-contract wallet. Other software reads ETH and may pay the address on Ethereum or another EVM chain, where a contract wallet at that address may not exist or may not be yours.

Subdomains

A record belongs to the exact name it is published at. To make shop.example.com payable, publish at that name:

shop.example.com. 3600 IN WALLET "ETH" "0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"
_wallet.shop.example.com. 3600 IN TXT "ETH 0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"

In the dashboard for the example.com zone, the TXT record's name is _wallet.shop. The Publish tab works this out for you.

  • Resolving. resolveWalletsUp, which the app's Pay tool and verifyPayTo use, falls back one level to the parent when a host publishes nothing, so api.example.com can be paid through the record of example.com. See Resolution.
  • Claiming. Escrow never falls back. Deposits are keyed by the exact name, and DnssecVerifier only accepts a record owned by that exact name or by _wallet. followed by that name. A parent's record cannot claim a subdomain's deposits.

Multiple addresses

Each record holds one coin code and one address. To publish several, add one record per address at the same name. zoneLines takes a list:

import { zoneLines } from './wallet262.js'

const { txt } = zoneLines('example.com', [
  { code: 'ETH', address: '0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de' },
  { code: 'BTC', address: 'bc1qxy2kgdygjrsqtzq2n0yrf2493p83kkfjhx0wlh' },
], 300)
console.log(txt.join('\n'))
_wallet.example.com. 300 IN TXT "ETH 0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"
_wallet.example.com. 300 IN TXT "BTC bc1qxy2kgdygjrsqtzq2n0yrf2493p83kkfjhx0wlh"

resolveWallets returns every record in records. A pair published both as a WALLET record and as a _wallet TXT record appears twice, once per source. The app's Pay tool lets the payer choose a record, and the CLI's link command uses the first EVM one.

Every EVM address that your signed record set publishes under an EVM coin code is a valid escrow claim recipient: the verifier accepts a claim to any record in the set whose address matches. Publish only addresses you control.

TTL

The TTL tells resolvers how long they may cache your record. zoneLines and the CLI's encode command default to 3600 seconds; the Publish tab offers 5 minutes, 1 hour (the default) and 1 day. Lower the TTL before you change an address, so payers stop seeing the old one sooner.

After you rotate to a new wallet, claim with the new record in the app's Escrow tab; when nothing is waiting, the button reads Register. The escrow remembers the signing time of the newest proof it has accepted for each domain and rejects any proof signed earlier with StaleProof, so an old signed record for your previous wallet can no longer claim later payments.

DNSSEC

DNSSEC signs your zone, so a resolver or a contract can prove that the record came from you. Without it, an attacker on the network path between a payer and the DNS could substitute their own address.

BehaviorUnsigned zoneSigned zone
resolveWalletsverified is always falseverified is true when the resolvers agree
App Pay toolSends, with a warning to double-checkMarks the address as signed and confirmed by every resolver
verifyPayTook on a match when the resolvers agree; strong is falseok and strong on a match when the resolvers agree
Escrow claimsNot possibleInstant

Resolving and paying trust the DNSSEC validation of the DNS-over-HTTPS resolvers, reported as the AD bit. Escrow claims trust no resolver: the contract checks the signatures itself, from the IANA root keys (KSK-2017 and KSK-2024) down to your record.

On-chain verification supports DNSSEC algorithms 5, 7, 8 and 13, which covers the root, .com and Cloudflare-signed zones. Zones signed with other algorithms, such as Ed25519 (15), aren't supported for claims.

To turn DNSSEC on, enable it at your DNS host, then add the DS record it gives you at your registrar if the registrar is a different company.

Resolution

How the SDK looks up a domain's wallets over DNS-over-HTTPS, cross-checks resolvers and DNSSEC, and reports what it found.

resolveWallets is the one lookup behind the app, the CLI and verifyPayTo. It asks two public DNS-over-HTTPS resolvers in parallel for both the native WALLET record and the _wallet TXT fallback, then tells you whether the answer can be trusted.

How a lookup works

  1. Normalize the name. normalizeDomain turns a domain, URL or email into a lowercase host name. Invalid input throws before any network request.
  2. Query every resolver. For each resolver, two DNS JSON queries run at once: type 262 at the domain, and type 16 (TXT) at _wallet.<domain>. The defaults are Cloudflare (https://cloudflare-dns.com/dns-query) and Google (https://dns.google/resolve).
  3. Parse the answers. Type 262 answers go through parseWalletRdata, which reads both the RFC 3597 generic form and quoted strings. TXT answers go through parseFallbackTxt. Each record is tagged with its source and with the AD bit of the response that carried it. Answers that fail to parse go to invalid.
  4. Compare resolvers. Resolvers that failed are set aside. The first resolver in your list that answered is the primary, and its records are returned. agree is true when every resolver that answered returned the same coin code and address pairs. Order does not matter, and EVM addresses are compared case-insensitively.
  5. Score the result. verified is true when there is at least one record, the resolvers agree, and every record is DNSSEC-authenticated.

Each query is a GET request with an accept: application/dns-json header:

GET https://cloudflare-dns.com/dns-query?name=yoursite.com&type=262
GET https://cloudflare-dns.com/dns-query?name=_wallet.yoursite.com&type=16

The SDK exports the values it uses: WALLET_TYPE (262), TXT_TYPE (16), FALLBACK_LABEL ('_wallet') and RESOLVERS, which maps cloudflare and google to their endpoints.

resolveWalletsUp

resolveWalletsUp(target, opts?) → Promise<Result & { resolvedAt, requested? }>

Resolves a host and, if it publishes nothing, its parent one level up: api.example.com falls back to example.com. The app's Pay tool and verifyPayTo use it, because the host a payer talks to is often an API subdomain.

ParameterTypeDescription
targetstringA domain, URL or email.
optsobjectThe same options as resolveWallets, plus walkUp: set it to false to disable the fallback.
import { resolveWalletsUp } from './wallet262.js'

const r = await resolveWalletsUp('https://api.yoursite.com/v1/data')
console.log(r.requested, r.resolvedAt)
// api.yoursite.com yoursite.com   (when only the parent publishes a wallet)

The walk follows these rules:

  • It goes up exactly one level. a.b.example.com falls back to b.example.com, never to example.com.
  • It does not walk when the host has records, when opts.walkUp is false, or when the host has fewer than three labels.
  • It stops before shared suffixes made of co, com, net, org, gov, edu, ac, or, ne or go followed by a two-letter label, such as co.uk or com.au. shop.co.uk is never resolved through co.uk.
  • If the parent has records, you get the parent's result with resolvedAt set to the parent and requested set to the original host. Otherwise you get the host's own result with resolvedAt set to the host and no requested.
The suffix check is a fixed pattern, not the Public Suffix List. A host under another shared suffix, such as myapp.vercel.app, falls back to vercel.app. Always show resolvedAt to the payer, as the app does, so they can see which name the wallet came from.

The rules, in order:

  1. Trim whitespace. Input without a scheme is read as http:// followed by the input, so text before an @ is dropped as user info, along with any path, query and port.
  2. Take the URL's host name. The URL parser converts internationalized names to punycode.
  3. Remove a trailing dot and lowercase the result.
  4. Require at least two labels and at most 253 characters. Every label but the last is 1 to 63 letters, digits, hyphens and underscores; it starts with a letter, digit or underscore and, when longer than one character, ends with a letter or digit. The last label is 2 to 63 letters, digits or hyphens.
Pass the normalized name to the escrow contracts. DomainEscrow accepts only lowercase ASCII names, with punycode for IDNs and no trailing dot, so that one domain can never end up with two pools. normalizeDomain produces names in that form.

What verified means

verified: true states three things at once:

  • The domain publishes at least one record.
  • Every resolver that answered returned the same coin code and address pairs.
  • Every returned record arrived in a response with the AD (Authenticated Data) bit set, meaning the resolver validated its DNSSEC signatures.

The SDK does not check DNSSEC signatures itself. It relies on the validation of the resolvers it queries, and by default it asks two independent operators and requires every one that answers to agree, which guards against a single bad resolver or a tampered network path. Escrow claims do not rely on this at all: the contract verifies the full signature chain on-chain. See DNSSEC proofs.

Agreement is measured among the resolvers that answered. If one resolver fails, agree and verified reflect the remaining resolver alone. When you need two independent answers, check resolvers as well:

import { resolveWallets } from './wallet262.js'

const r = await resolveWallets('yoursite.com')
const independent = r.verified && r.resolvers.every(x => x.ok)

Build

SDK

Resolve and verify WALLET records, generate zone lines and build payments with one dependency-free ES module that runs in browsers and Node 18+.

The SDK is a single ES module, lib/wallet262.js, with no dependencies. Use it to resolve a domain to its wallets, check that a payment address really belongs to a domain, generate the records to publish, and build transfers and payment links. It runs in browsers and in Node 18 or later, using only fetch and DNS-over-HTTPS JSON. The TYPE/262 app, the landing page and the CLI all import this same file.

Install

Download the module from the TYPE/262 site and import it by path:

curl -O https://type262.onrender.com/lib/wallet262.js
import { resolveWallets, verifyPayTo } from './wallet262.js'

In the browser or Deno you can import it straight from the site:

import { resolveWallets } from 'https://type262.onrender.com/lib/wallet262.js'

It is ESM only; from CommonJS, load it with await import('./wallet262.js'). It has no dependencies.

In the browser

The module imports nothing, so you can copy lib/wallet262.js next to your page and load it from a module script. Serve the page over HTTP; ES modules do not load from file://.

  const r = await resolveWallets('yoursite.com')

</script>
Every network request goes to the public DNS-over-HTTPS endpoints in RESOLVERS (Cloudflare and Google), or to the endpoints you pass in opts.resolvers. There is no TYPE/262 server in the path.

Resolve

Both resolve functions accept a domain, a URL or an email address. They query every resolver in parallel for the WALLET record and the _wallet TXT fallback, then report whether the resolvers agree and whether the answers are DNSSEC-authenticated. Resolution describes the algorithm in depth.

resolveWallets(input, opts?) → Promise<Resolution>

Resolves the wallets published by one name. For each resolver it sends two DoH queries at once: type 262 at the domain and, unless you turn it off, TXT at _wallet.<domain>. The returned records, invalid and nxdomain come from the first resolver in the list that answered, which is Cloudflare by default. Every resolver that answered counts toward agree and dnssec.

normalizeDomain(input) → string

Reduces a domain, URL or email to a lowercase hostname. It parses the input with URL, so internationalized names become punycode and the user part of an email is dropped. A trailing dot is removed. Checks that a coin code fits the address it is published with. An EVM address needs a code in EVM_CODES, a Bitcoin address needs BTC, and a Solana address needs SOL. For any other address it returns true. The code is compared case-insensitively.

Agents and x402

Before an agent pays an x402 requirement, check that the address it was given is the one the payee domain publishes.

An HTTP 402 Payment Required response tells a client where to send money, in a payTo field. Nothing in the response proves that the address belongs to the service you think you are paying. A compromised server, a proxy or a typo-squatted host can swap it. TYPE/262 closes that gap: the payee publishes its address in DNS, and the agent checks the payTo against that record before it signs anything.

The check

  1. Read the requirement. payTosFromX402(body) pulls every payTo out of the 402 response.
  2. Verify each address. verifyPayTo(target, payTo) resolves the domain you are paying and looks for a published record with that address.
  3. Decide. Pay only on a match. Apply a stricter policy to unsigned zones, and never pay when the resolvers disagree.
import { payTosFromX402, verifyPayTo } from './wallet262.js'

const res = await fetch('https://api.yoursite.com/report')
if (res.status === 402) {
  const body = await res.json()
  for (const payTo of payTosFromX402(body)) {
    const check = await verifyPayTo('https://api.yoursite.com/report', payTo)
    if (!check.strong) throw new Error(`Refusing to pay ${payTo}: ${check.reason}`)
  }
  // every payTo is published by yoursite.com, DNSSEC-signed, and the resolvers agree: pay
}

Reading the 402 body

payTosFromX402(body) accepts the parsed JSON or the raw string. It reads the accepts array (x402) or a paymentRequirements array, falls back to a bare array or a single requirement object, and returns every payTo (or pay_to) it finds. A string that isn't valid JSON throws.

  "x402Version": 1,
  "accepts": [
    {
      "scheme": "exact",
      "network": "base",
      "maxAmountRequired": "10000",
      "resource": "https://api.yoursite.com/report",
      "payTo": "0x7a1fe1c2b0d3a4f5e6d7c8b9a0f1e2d3c4b5c0de"

}

verifyPayTo returns every field of the resolution plus ok, strong, reason and match. The address is compared case-insensitively for EVM addresses and exactly for everything else; the coin code is not compared. The first rule that applies sets reason:

Which domain is checked

target can be a URL, an email address or a bare domain; it is normalised with normalizeDomain. Verification uses resolveWalletsUp: if the host publishes nothing and has at least three labels, its parent is checked too, so api.yoursite.com can rely on the record at yoursite.com. The walk stops below multi-label public suffixes such as co.uk, and you can turn it off with { walkUp: false }. The result's resolvedAt tells you where the record was found, and requested holds the original host when the parent was used.

Check the domain you are actually talking to, taken from the URL you requested. Never take the domain from the 402 body itself: a tampered response would simply name a domain the attacker controls.

Recommended policy

  • Require strong for autonomous payments. It means the record is DNSSEC-signed and both resolvers agree.
  • Treat ok without strong as unverified. Cap the amount or ask for approval.
  • Refuse on !ok, and log reason and resolvers for review.
  • Re-check per payment. Records can change; the check costs two DNS-over-HTTPS queries per name.

In the app

The app's Verify tab runs the same check. Give it a URL or domain and either a payTo address or a whole 402 body. Each address gets one of three verdicts: Match. Safe to pay. (strong), Match, unsigned. (ok only) or No match. Don't pay.

Payments

Pay a domain by name: resolve its wallet, check the answer, then send USDG or ETH on Robinhood Chain.

Paying a name is three steps: resolve the domain to the wallets it publishes, decide whether you trust the answer, and send. The SDK gives you each step; the app's Pay tab does all three with a browser wallet.

Resolve and check

import { resolveWalletsUp } from './wallet262.js'

const r = await resolveWalletsUp('yoursite.com')
if (!r.records.length) throw new Error('yoursite.com publishes no wallet')
if (!r.agree) throw new Error('Resolvers disagree: possible tampering')
const record = r.records.find(x => x.code === 'ETH') ?? r.records[0]
console.log(record.address, r.verified ? 'DNSSEC-verified' : 'unsigned zone')

Contracts

Escrow

Pay a domain before it publishes a wallet: its owner claims with an on-chain DNSSEC proof, and unclaimed deposits come back after the refund delay.

Pay any domain before it publishes a wallet. DomainEscrow holds the money on Robinhood Chain in a pool keyed by the domain name. The domain's owner claims it whenever they are ready by proving, with DNSSEC, which wallet the domain publishes. If nobody claims, each depositor takes their own deposit back after the refund delay.

No server, attestor or admin decides who gets paid. The proof is checked on-chain by DnssecVerifier and the DNSSEC oracle it calls (see DNSSEC proofs), and the escrow only ever pays the wallet that proof shows. If the domain already publishes a wallet, pay it directly instead (see Payments).

How it works

depositor ──deposit / depositToken────────────────▶ DomainEscrow   one pool per (domainHash, token)
anyone    ──claim(domain, wallet, proof, tokens)──▶ DomainEscrow ──verify──▶ DnssecVerifier ──▶ ENS DNSSEC oracle
                                                    │
                                                    └──▶ proven wallet: each listed pool, minus the claim fee

  1. A depositor calls deposit (ETH) or depositToken (ERC-20) with the domain name. The amount joins the pool for that domain and token, and the contract records what this depositor put in.
  2. The domain's owner publishes a wallet record, signs the zone with DNSSEC and submits a claim carrying a proof. Anyone can submit it. The money can only go to the wallet the proof shows.
  3. The claim pays each listed token's entire pool to that wallet in the same transaction, minus the fee.
  4. If no claim pays out a pool, each depositor can refund their own deposit once refundDelay has passed since their latest deposit to it.

Claims

claim(domain, recipient, proof, tokens) pays every listed pool to recipient, minus the fee. In order, it:

  1. Checks that domain is canonical (BadDomain) and that recipient is not the zero address (BadRecipient).
  2. Calls verifier.verify(domain, recipient, proof). This reverts unless the proof shows the domain publishing recipient, and returns the time the record was signed.
  3. Reverts with StaleProof if that signing time is older than the newest proof already used for this domain, then stores it.
  4. For each token with a non-zero pool: empties the pool, advances its epoch, sets the fee aside, sends the rest to recipient and emits Claimed.

Anyone can submit a claim, including a relayer. The sender receives nothing, so the receiving wallet never needs gas. The admin cannot pause or block claims. If a transfer to recipient fails, for example because it is a contract that rejects ETH, the whole claim reverts with TransferFailed and nothing moves.

Claims are instant. Whoever controls a domain's DNS, with DNSSEC on, can claim everything waiting for it. Protect your registrar and DNS host accounts the way you protect a wallet key.

Newer signatures win

For each domain the escrow stores the signing time of the newest proof it has accepted, in lastProof(domainHash). A claim whose proof was signed earlier reverts with StaleProof. A proof with the same signing time is accepted. The signing time is the inception of the signature over the wallet record, as returned by signedAt.

This blocks replays. A DNSSEC signature stays usable until it expires, so without this rule a previous owner, or a wallet you have since replaced, could reuse an older signed record. Once a newer record has been used, older ones can never claim this domain's funds again.

Registering a record with an empty pool

A claim succeeds even when every listed pool is empty. It pays nothing, but it still stores the proof's signing time. Use it to lock out older records as soon as you take over a domain or rotate its wallet, before anyone pays it. In the app, the claim button reads Register when nothing is waiting.

cast send $ESCROW "claim(string,address,bytes,address[])" \
  yoursite.com 0xYourWallet "$(cat proof.hex)" "[]" \
  --account my-wallet --rpc-url $RPC

# The stored signing time for the domain
cast call $ESCROW "lastProof(bytes32)(uint64)" $(cast keccak yoursite.com) --rpc-url $RPC

Refunds

refund(domain, token) returns your whole deposit in that pool to you once refundDelay has passed since your latest deposit to it. Before then it reverts with RefundLocked. Only the depositor can refund a deposit, because the funds always go to msg.sender. Refunds keep working while deposits are paused.

Topping up restarts the clock. Each deposit sets the unlock time for your entire balance in that pool, not just the new amount.

refundableOf(domain, token, depositor) returns (amount, unlocksAt). Treat amount == 0 as nothing to refund and ignore unlocksAt in that case.

cast call $ESCROW "refundableOf(string,address,address)(uint256,uint64)" \
  yoursite.com $USDG 0xYourAddress --rpc-url $RPC

cast send $ESCROW "refund(string,address)" yoursite.com $USDG --account my-wallet --rpc-url $RPC

Claimed deposits can't be refunded

Each pool has an epoch counter. A claim that pays out a pool advances its epoch, and every deposit records the epoch it was made in. A deposit from an earlier epoch has already been paid to the domain, so:

  • refund reverts with NothingToRefund, even after the delay.
  • refundableOf returns (0, 0).
  • If you deposit again, the stale amount is discarded and your new deposit starts fresh in the current epoch.

Epochs are per token. A claim that lists only ETH leaves the USDG pool, and refunds against it, untouched.

Fees

The escrow charges only when it pays out a claim. Deposits and refunds are free.

  • The fee is amount * feeBps / 10_000 per token, rounded down. feeBps is fixed at deploy and capped by MAX_FEE_BPS (100, or 1%); the constructor reverts with BadConfig above that.
  • On the live deployment a claim on a 100 USDG pool sends 99.5 USDG to the wallet and sets 0.5 USDG aside. The Claimed event reports the net amount and the fee separately.
  • A claim never sends the fee. It adds the fee to feesOwed[token], and withdrawFees(token) later sends the full amount owed to feeRecipient. Anyone can call it. It reverts with ZeroAmount when nothing is owed.
  • Because claims never send to the fee recipient, a fee address that can't receive, such as a reverting contract or an address a token has frozen, can never block a claim.
  • The fee also applies to launch creator fees, which reach the escrow as deposits from the domain's DomainFeeForwarder (see Launchpad).

What the admin can do

The admin has one switch, setDepositsPaused(bool). While it is on, deposit and depositToken revert with Paused. Claims, refunds and withdrawFees keep working. The role moves in two steps: transferAdmin(to), then acceptAdmin() from the new address.

That is the complete list. verifier, refundDelay, feeBps and feeRecipient are immutable, and no function lets the admin move pooled funds, choose a recipient, or delay a claim or refund.

Pausing also makes DomainFeeForwarder.flush revert whenever it has something to deliver, because it delivers launch fees as deposits. Those fees stay at pons until deposits resume, and the app disables Collect to escrow while deposits are paused.

Canonical domain names

  • Only lowercase a-z, digits 0-9, hyphen and underscore. Internationalized names must be in punycode.

DNSSEC proofs

How DnssecVerifier proves on-chain, from the IANA root keys down, which wallet a domain publishes, and how to build a proof it accepts.

Every escrow claim carries a DNSSEC proof: the chain of signed DNS record sets from the root zone down to the domain's wallet record. DnssecVerifier hands the chain to ENS's DNSSEC oracle, which verifies every signature on-chain, starting from the IANA root trust anchors, then reads the wallet out of the final record set. Nothing built off-chain is trusted, and nobody, including the deployer, can change how proofs are checked.

This is stricter than resolution. Resolve and Pay trust the DNSSEC check of the DNS-over-HTTPS resolvers (see Resolution); escrow claims verify the signatures themselves.

Chain of trust

IANA root DS 20326, 38696                  trust anchors stored in the oracle
└─ .  DNSKEY                               verified against the anchors
   └─ com.  DS                             signed by the root zone
      └─ com.  DNSKEY
         └─ yoursite.com.  DS              signed by com.
            └─ yoursite.com.  DNSKEY
               └─ _wallet.yoursite.com.  TXT  "ETH 0x…"

Each line below the anchors is one signed record set in the proof, and the oracle verifies each one against the set above it. The length depends on the zone: the proof for the TXT record at cloudflare.com in contracts/test/fixtures/proof.hex has six sets.

The oracle

Supported zones

A zone can claim when every signature in its chain uses algorithm 5, 7, 8 or 13, and each delegation has a DS record with digest type 1 or 2. That covers the root, .com and Cloudflare-signed zones.

Zones signed with Ed25519 (algorithm 15) cannot claim yet, and neither can zones using any other algorithm missing from the list, such as 14 (ECDSAP384SHA384). The oracle has no verifier for them. The proof builder, @ensdomains/dnsprovejs, only knows algorithms 5, 7, 8 and 13 and digests 1 and 2, so it cannot complete the chain and the claim stops before a transaction is sent.

make-proof.mjs prints the algorithm of every set it collects, which is the quickest way to check a zone (see Building a proof from a script). For a zone it cannot prove, it fails instead with NoValidDnskeyError or NoValidDsError from dnsprovejs.

Accepted records

Once the oracle accepts the chain, verify walks the records of the final set. It succeeds on the first record of class IN that matches one of these and publishes the claimed recipient:

Everything else is ignored: a TXT record at the domain itself, records for any other name, and lines for non-EVM coins in the same set. If nothing matches, verify reverts with NotPublished. The TXT form works on every DNS host and is the record the app proves. See The WALLET record for how to publish both.

Parsing rules

walletAddress(rdata) extracts the address from a record. It is deliberately strict, so a mangled record can never be read as some other address.

  • Shape. RDATA is either exactly two character-strings, "COIN" "0x…", or one character-string, "COIN 0x…" or "COIN:0x…", where any run of spaces and colons separates the parts. Three or more strings, truncated data, or anything after the address yield nothing.
  • Coin. Must be an EVM coin, in any letter case: ETH, EVM, HOOD, USDG, ARB, OP, POL, USDC, USDT or DAI. Each of these is published as a plain EVM address, the same key on Robinhood Chain.
  • Address. Exactly 0x (or 0X) followed by 40 hex digits in any case. Longer values are never truncated. EIP-55 checksum casing is not enforced.
  • Failure. A record that breaks any rule parses to address(0), and verify rejects address(0) as a recipient, so no claim can reach the zero address through a BTC, SOL or malformed line.

Proof format

The proof argument of claim and verify is the ABI encoding of an array of the oracle's RRSetWithSignature struct:

// @ens/dnssec-oracle/DNSSEC.sol, inside abstract contract DNSSEC
struct RRSetWithSignature {
    bytes rrset; // RRSIG RDATA without the signature, then the signed records in canonical wire form
    bytes sig;   // the RRSIG signature
}

// proof = abi.encode(DNSSEC.RRSetWithSignature[])
  • Sets run from the root down. The first is verified against the root anchors, each later set against the one before it, and the last set must hold the wallet record.
  • The oracle checks every signature's validity window at the current block time and reverts with SignatureExpired or SignatureNotValidYet outside it. Build the proof shortly before you submit it.
  • verify returns the inception time of the last set's signature, converted by signedAt. The escrow uses it to enforce newer signatures win.

Signing time

The oracle accepts a signature inception up to 2^31 seconds in the past, using RFC 1982 serial-number arithmetic. The raw uint32 can therefore be numerically larger than the current time even though it is in the past. If the escrow compared raw values, one old signature could look newer than every real one and block all future claims.

signedAt avoids this by counting back from the current block time:

function signedAt(uint32 inception) public view returns (uint64) {
    uint32 age;
    unchecked {
        age = uint32(block.timestamp) - inception;
    }
    return age > block.timestamp ? 0 : uint64(block.timestamp - age);
}

The result is never later than the current block. A signature older than the Unix epoch counts as 0.

Launchpad

Launch a pons v2 token whose creator fees go to a domain, then collect and claim those fees through escrow.

Launch a token on pons v2, Robinhood Chain's launchpad, with its creator fees routed to a domain instead of a wallet. Fees build up for the domain from the first trade, even before the domain publishes a wallet. The domain's owner claims them from DomainEscrow with the same DNSSEC proof as any escrow payment.

How fees reach a domain

launch ──▶ DomainLauncher ──▶ pons factory   (creatorFeeRecipient = the domain's forwarder)
trades ──▶ pons fee escrow ──collect(domain)──▶ DomainFeeForwarder ──▶ DomainEscrow ──claim──▶ domain owner

  3. Collect. Anyone calls collect. It deploys the forwarder on first use, sweeps the domain's curves, pulls ETH and the listed tokens (the app lists USDG) from pons and deposits them into DomainEscrow under the domain.
  4. Claim. The domain's owner claims from escrow with a DNSSEC proof of the domain's _wallet record, checked on-chain. See DNSSEC proofs.

What the launcher enforces

  • Fees always go to the domain. creatorFeeRecipient is replaced with the domain's forwarder. Whatever you pass is ignored.
  • Buyback is off. buybackEnabled is forced to false. Only the fee recipient could change it later, and the forwarder never does.
  • Exact payment. msg.value must cover openingBuy, and the rest must equal pons.launchFee().
  • Opening buy. ETH pairs only. The launcher calls curve.buy(openingBuy, minTokensOut, msg.sender) on the new curve, so the tokens go to you. If the buy fills the curve and it graduates, the ETH the curve couldn't take is refunded to you in the same transaction.
  • Snipe-tax exemption. Your address is passed to pons as the launch's snipe-tax exemption, so your own opening buy skips the launch snipe tax.
  • No custody. The launch fee and the opening buy pass straight through to pons. The launcher keeps nothing and rejects direct ETH transfers.

The fee forwarder

Each domain has exactly one DomainFeeForwarder. The launcher deploys it with CREATE2, using keccak256(bytes(domain)) as the salt and (domain, DomainEscrow, pons fee escrow) as constructor arguments, so its address is fixed before it exists. pons can credit fees to it from the first trade; the contract itself is deployed by the first collect, collectPools or deployForwarder call for the domain.

  • It has no owner and no admin functions.
  • It never calls pons's transferCreatorFeeRecipient or setBuybackEnabled, so it can't redirect fees or turn buyback on.
  • Its only destination is DomainEscrow, under its own domain. Its constructor reverts with BadDomain for a non-canonical name.

The token page reads any pons v2 token from the pons factory and shows its pair, its phase (bonding curve or graduated), where its creator fees go, its market cap, the amount raised, its graduation target and its creator fee. Tokens not launched through DomainLauncher are labelled as not paying a domain.

On the curve you can buy and sell directly. The quote uses the curve's constant-product formula after the curve fee, the creator tax and any launch snipe tax; the app re-reads the reserves right before sending and allows at most 5% slippage. USDG buys and all sells ask for a token approval first if needed. Graduated tokens link to pons for trading.

Collect

The fee panel appears on a domain's board and on the page of any token launched through DomainLauncher. It shows what pons holds for the domain, what is already in escrow and ready to claim, a Collect to escrow button and a link to claim in the Escrow tab. The button calls collect(domain, curves, [USDG]), where curves are the board's launches that haven't graduated (on a token page, that token's curve alone).

Trust notes

pons's owner can redirect fees. It can move any pons token's creator fee recipient, a domain's forwarder included, behind a public 3-day timelock. The forwarder can't prevent that. For tokens launched through DomainLauncher, the token page compares the token's live fee recipient with forwarderOf(domain), checks pons's pending recipient, and warns if the fees have moved or a move is pending.
  • Fees after graduation. Once a curve graduates, its liquidity moves to Uniswap v4 and creator fees accrue in pons's hook. pons's operator sweeps them, and collectPools lets the forwarder sweep its own pools. The app's Collect button on a graduated token moves only what pons already holds for the domain.
  • Fee accounting is pons's. The launcher and the forwarder rely on pons v2's factory, curves, fee escrow and hook to credit fees correctly.

Self-hosting

Run the site locally, deploy it to any static host, configure the app, and deploy your own contracts.

The site is plain static files: no build step and no backend. Claims are DNSSEC proofs checked on-chain, so a copy of the site needs only a static host, plus the optional upload service if you want image uploads in the Launch form. You can run your own copy against the live contracts without changing anything, or deploy your own contracts and point the app at them.

Run the site locally

# from the project folder
npm run dev

npm run dev runs python -m http.server 5262 --bind 127.0.0.1, so it needs Python 3. Open http://127.0.0.1:5262 for the landing page, /app.html for the app and /docs.html for these docs. The pages load ES modules, so they must be served over HTTP: opening the files directly won't work.

Deploy your own contracts

You need this only for a separate deployment, for example on a fork of the project. One script checks the network, your balance and the tests, dry-runs the deploy with its real cost, and asks for confirmation before it sends anything. Run every command from the repository root in a Bash shell (Git Bash on Windows).

You need Foundry (forge and cast in ~/.foundry/bin), Node 18 or later, and about 0.001 ETH for the deployer on Robinhood Chain, not on Ethereum. DEPLOY.md puts the cost at about 0.0003 ETH, for around 10.8M gas.

  1. Fetch the contract libraries. contracts/lib holds pinned git submodules: 
    git submodule update --init --recursive
  2. Create a deployer key. Either put a dedicated hot wallet in ~/.type262/deployer.env, outside any synced folder, with the two lines DEPLOYER=0x… and DEPLOYER_PRIVATE_KEY=0x…, or import a key into Foundry's encrypted keystore.     cast wallet import deployer --interactive

  4. Deploy. Set the admin and fee recipient to your main wallet so the deployer key controls nothing afterwards, and get the leftover gas back: 
    OWNER=0xYourMainWallet SWEEP_TO=0xYourMainWallet bash contracts/script/deploy-robinhood.sh
  5. Point the app at your contracts. This checks the deployment on-chain and writes assets/config.js. Commit assets/config.js and deployments/; on Render, the push redeploys the site.

What the deploy script does

  1. Network. Checks that the RPC answers chain 4663.
  2. Wallet and settings. Checks that the deployer holds at least MIN_ETH and prints the admin, fee recipient, fee, refund delay and pons factory.
  3. Tests. Runs forge test --fuzz-runs 1000.
  4. Dry run. Simulates Deploy.s.sol against mainnet and shows the estimated cost. Nothing is sent.
  5. Deploy. Stops if a deployment record already exists, waits for you to type DEPLOY, broadcasts, and saves the addresses to deployments/robinhood-4663.json.
  6. Verify source. Verifies all nine contracts on Sourcify, or on Blockscout with VERIFIER=blockscout.

Deploy.s.sol deploys ENS's DNSSECImpl with the IANA root anchors, sets algorithms 5, 7, 8 and 13 and digests 1 and 2, renounces the oracle's ownership, then deploys DnssecVerifier, DomainEscrow and DomainLauncher. If SWEEP_TO is set, the script finally sends the deployer's remaining ETH there, keeping three times the transfer's estimated gas cost.

Operate a deployment

The admin has one switch: pausing new deposits. Claims and refunds keep working while deposits are paused. Pausing also stops launch fees from being collected into escrow; they wait at pons until deposits resume.

ESCROW=0x9fd2f1Dc0B42e8a2E86e3Cf231a293654691E8d5   # your DomainEscrow
RPC=https://rpc.mainnet.chain.robinhood.com
ADMIN=admin   # the Foundry keystore that holds the escrow admin key (OWNER)

# Pause new deposits (admin only); pass false to resume
cast send $ESCROW "setDepositsPaused(bool)" true --account $ADMIN --rpc-url $RPC

# Send accrued claim fees to the fee recipient: ETH, then USDG (any account can send these)
cast send $ESCROW "withdrawFees(address)" 0x0000000000000000000000000000000000000000 --account $ADMIN --rpc-url $RPC
cast send $ESCROW "withdrawFees(address)" 0x5fc5360D0400a0Fd4f2af552ADD042D716F1d168 --account $ADMIN --rpc-url $RPC

withdrawFees reverts with ZeroAmount when nothing is owed for that asset. To hand over the admin role, the current admin calls transferAdmin(newAdmin) and the new admin calls acceptAdmin().

If Sourcify verification doesn't finish, the contracts are still deployed. Verify by hand on Blockscout with Verify & Publish and Solidity (Standard JSON input), generating the input with forge verify-contract <address> src/DomainEscrow.sol:DomainEscrow --show-standard-json-input from contracts/. Use compiler 0.8.28, the optimizer at 10,000 runs and EVM version shanghai.

What the simulations prove:

  • Escrow lifecycle. USDG and ETH sent to a domain that hasn't published anything wait in escrow. A proof can't pay any wallet but the published one, and another domain's proof can't pay this one. Anyone can submit the proof; the owner receives 99.5% instantly and the fee is withdrawn to the treasury. An older signature is refused, a pause blocks deposits while claims still pay, and claimed money can't be refunded.
  • Refunds. An unclaimed deposit is locked until the 180-day delay passes, then refunded in full.
  • WALLET at the apex. A type 262 record at the domain itself claims as well as the _wallet TXT record.
  • ETH launch. A launch with an opening buy sends the tokens to the creator, sets the domain's forwarder as pons's fee recipient and leaves nothing in the launcher. One collect moves the fees into escrow, leaving nothing at pons or in the forwarder, and the owner claims them minus 0.5%.
  • USDG launch. The same flow on a USDG pair. The new curve's reserves, 3,236 USDG of phantom reserve against the full 1,000,000,000-token supply, match what the app assumes.
  • App quotes. The app's buy and sell estimates match the real curve within 1%.
  • Graduation. pons graduates the curve when the raised amount the app shows reaches the curve's threshold; a pool sweep that can't happen yet is skipped instead of reverting, and collect keeps working after graduation.
  • Launch guards. Buyback is off even when requested, an oversized opening buy fills the curve and refunds the rest, and the launcher rejects direct payments.
  • Registry. A non-canonical name, a wrong payment and an opening buy on a USDG pair revert; a fee recipient passed in is ignored; the registry pages newest first; the forwarder deploys once, at the predicted address.

Security

The trust model, how claims are verified, the specifications, and how to report a vulnerability privately.

TYPE/262 takes the attestor and the server out of claims. The escrow pays only a wallet that a DNSSEC proof shows, and the contract checks that proof on-chain, from the DNS root keys down. What remains to trust is DNS itself, the code and, for launches, pons. This section sets out exactly what that means.

Trust model

You rely onFor
ENS's DNSSEC oracle and the IANA root keysChecking proofs. DNSSECImpl is ENS's production code, anchored to the root KSK-2017 and KSK-2024. Its ownership is renounced, so nobody can change its algorithms or anchors.
Your DNS host and registrarControl of the domain. Whoever controls a DNSSEC-signed zone can publish a _wallet record and claim that domain's escrow, instantly.
Cloudflare and Google DNS-over-HTTPSOff-chain answers. Resolve, Pay, Verify, the SDK and the CLI trust these resolvers' DNSSEC validation (the AD bit) and flag any disagreement between them.
pons v2Launch fees. pons's contracts create, hold and sweep creator fees, and pons's owner can redirect a token's fee recipient behind a 3-day timelock.
The escrow adminPausing new deposits and handing the admin role over in two steps. Nothing else.

What you don't need to trust

  • A server. No attestor or backend takes part in a claim. Your browser builds the proof from public DNS data, and the contract verifies every signature.
  • Whoever submits the proof. Anyone can submit it, a relayer paying the gas for example, and the money still goes only to the wallet the proof shows.
  • The admin. It can't move funds, change who gets paid, change the fee or the refund delay, or block claims and refunds.
  • The fee recipient. Claim fees are set aside and sent later with withdrawFees, so a fee address that can't receive never blocks a claim.
  • The fee forwarder. It has no owner and can only deposit into its own domain's escrow pool.

How it's verified

Claims are checked by ENS's DNSSEC oracle, the production code that verifies DNS names on Ethereum, anchored to the IANA root keys with its ownership renounced. The TYPE/262 contracts are open source and verified on Sourcify, and they are covered by unit tests, fuzzing and simulations against Robinhood Chain mainnet, including real DNSSEC proofs and the live pons contracts. See Testing and Deployments.

Instant claims

There is no waiting period. Whoever controls a domain's DNS, with DNSSEC on, can claim the domain's escrow and its launch fees in one transaction. Protect your registrar and DNS host accounts as carefully as a wallet key.

Escrow orders proofs by when the DNS data was signed. A proof signed earlier than the last one used reverts with StaleProof, so a previous owner's old signed record can't be replayed over a newer one. Use this when a wallet or an owner changes:

  1. Publish the new record. Update _wallet.<domain> to the new wallet, with DNSSEC on.
  2. Register it. In the app's Escrow tab, Register (shown when nothing is waiting) submits a proof of the current record without moving money. From then on, a record signed before it, such as one naming an old wallet, can never claim later payments.

Resolver trust and on-chain verification

Two different guarantees apply, depending on what you do:

FeatureHow the record is checked
Resolve, Pay, Verify (x402 payTo), the SDK and the CLIOff-chain, through Cloudflare and Google DNS-over-HTTPS. You trust the resolvers' DNSSEC validation. verified is true only when records exist, every resolver that answered agrees, and every record is DNSSEC-authenticated. verifyPayTo reports strong when the address matches, the resolvers agree and the matching record is DNSSEC-authenticated.
Escrow claims, including launch feesOn-chain. DnssecVerifier has ENS's oracle check the full signature chain from the root keys. No resolver is trusted.

Before a direct payment, require verified (or strong) rather than just a match. See Resolution and Payments.

Launchpad trust

  • pons's owner can redirect fees. It can move any pons token's creator fee recipient behind a public 3-day timelock, and the forwarder can't stop it. The token page warns when that has happened or is pending.
  • Fees need a sweep. Curve fees reach pons's fee escrow only when someone sweeps them; pons's operator does, and so does Collect. After graduation, fees sit in pons's Uniswap v4 hook until swept. collectPools can sweep them; the app doesn't call it yet.
  • pons accounts for fees. The launcher and the forwarder rely on pons's contracts to credit fees correctly.
  • A deposit pause also pauses collection. Fees stay at pons until deposits resume.

See Launchpad for the full flow.

Specifications

  • DNSSEC algorithms. The oracle supports algorithms 5, 7, 8 and 13, which covers the root, .com and Cloudflare-signed zones. Zones signed with other algorithms, such as Ed25519 (15), aren't supported for claims.
  • Records. The contract accepts _wallet.<domain> TXT and WALLET (type 262) at the domain itself. The app builds proofs for the TXT record only.
  • Coins and addresses. Only EVM coin codes count (ETH, EVM, HOOD, USDG, ARB, OP, POL, USDC, USDT, DAI), with exactly 0x plus 40 hex digits. Anything else in the record is ignored and can never be claimed to.
  • Names. Escrow accepts only canonical names: lowercase ASCII with punycode for IDNs, labels of 1 to 63 characters, 253 characters at most. Anything else reverts with BadDomain, so one domain can never end up with two pools.
  • Wallet type. Publish a regular wallet address, not a multisig or smart-contract wallet: other apps read ETH and may pay it on Ethereum or other EVM chains.
  • Refunds. A sender can take a deposit back 180 days after their last deposit to that domain and asset, and only if no claim has paid that pool out since. Collected launch fees stay with the domain until its owner claims them.
  • Immutability. The fee, fee recipient and refund delay are fixed at deploy, and the contracts are not upgradeable, so the rules never change under you.

Report a vulnerability

Report security issues privately to the maintainers, and don't disclose them publicly until a fix is deployed.

Say which component is affected (a contract, the SDK, the CLI, the app, the scripts or the upload service), how to reproduce the issue and what impact you see. For a contract issue, a Foundry test against a Robinhood Chain fork is the clearest reproduction.

Conventions

  • No build step. Pages load native ES modules straight from assets/ and lib/. scripts/build.sh only copies files and versions asset paths.
  • Vanilla JavaScript. No framework and no bundler. The package is "type": "module".
  • A zero-dependency SDK. lib/wallet262.js imports nothing and runs in browsers and Node 18+ with fetch and DNS-over-HTTPS JSON. The upload service has no dependencies either.
  • No runtime packages in the app. The app encodes contract calls with its own small ABI coder, which test/abi.test.mjs checks against viem, and loads a pinned, vendored copy of dnsprovejs. viem and dnsprovejs are dev dependencies only.
  • Formatting. Match the existing JavaScript: two-space indentation, no semicolons, single-quoted strings.
  • Solidity. pragma solidity ^0.8.24, built with solc 0.8.28, the optimizer at 10,000 runs and EVM version shanghai. Custom errors, NatSpec comments, and an MIT SPDX header on every file. The contracts have no proxies, and the admin has no power over funds.
